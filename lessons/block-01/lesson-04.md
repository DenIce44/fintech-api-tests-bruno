**Продолжительность:** 90 минут

## 2. Разберите три разных контракта ответа — 10 минут

После занятия 3 у вас уже есть запрос одного ресурса:

```http
GET /posts/1
```

Его успешное тело — JSON-объект:

```json
{
  "userId": 1,
  "id": 1,
  "title": "...",
  "body": "..."
}
```

На занятии 4 появится запрос коллекции:

```http
GET /posts?userId=1
```

Его тело — массив объектов:

```json
[
  {
    "userId": 1,
    "id": 1,
    "title": "...",
    "body": "..."
  }
]
```

Если фильтру не соответствует ни одна запись, JSONPlaceholder возвращает успешную пустую выборку:

```http
GET /posts?userId=999999
```

```json
[]
```

Сравните три сценария:

| Сценарий | Статус | Тип тела | Смысл |
|---|---:|---|---|
| Существующий `/posts/1` | `200` | object | Один ресурс найден |
| Фильтр с совпадениями | `200` | array, не пустой | Коллекция успешно получена |
| Фильтр без совпадений | `200` | пустой array | Запрос корректен, результатов нет |
| Несуществующий `/posts/999999` | `404` | object | Конкретный ресурс не найден |

`200 + []` и `404` не взаимозаменяемы. Фильтр задаёт корректную коллекцию, в которой может не быть элементов. URL конкретного ресурса утверждает, что клиент ищет одну сущность по идентификатору.

Контракт ответа включает не только статус. Для текущих запросов он описывает как минимум:

- HTTP-статус;
- `Content-Type`;
- верхнеуровневый тип JSON: object или array;
- обязательные поля элементов;
- типы полей;
- связь результата с входным фильтром.

### 4.1. Создайте запрос

- метод: `GET`;

Во вкладке **Params** добавьте включённую строку:

| Name | Value |
|---|---|
| `userId` | `{{postUserId}}` |

Итоговый URL после подстановки:

```text
https://jsonplaceholder.typicode.com/posts?userId=1
```

Сохраните и отправьте запрос. Ожидается:

- статус `200 OK`;
- `Content-Type` содержит `application/json`;
- тело является массивом;
- массив не пуст;
- каждый элемент содержит `userId`, `id`, `title`, `body`;
- у каждого элемента `userId` равен `1`.

### 4.2. Добавьте декларативные assertions

Во вкладке **Assert** добавьте:

| Expression | Operator | Value | Что проверяет |
|---|---|---|---|
| `res.status` | `equals` | `200` | фильтр обработан успешно |
| `res.headers['content-type']` | `contains` | `application/json` | сервер вернул JSON |
| `res.body[0].userId` | `equals` | `1` | первый элемент соответствует фильтру |

Декларативная проверка первого элемента полезна, но недостаточна: второй или последующий элемент всё ещё может нарушить фильтр. Поэтому полный контракт массива проверяется JavaScript-тестом.

### 4.3. Добавьте JavaScript-тесты

Во вкладке **Tests** добавьте:

```javascript
test("filtered posts return a non-empty JSON array", function () {
  const posts = res.getBody();

  expect(res.getStatus()).to.eql(200);
  expect(res.getHeader("content-type")).to.include("application/json");
  expect(posts).to.be.an("array").that.is.not.empty;
});

test("every post has the expected contract", function () {
  const posts = res.getBody();

  posts.forEach(function (post) {
    expect(post).to.be.an("object");
    expect(post).to.have.all.keys("userId", "id", "title", "body");
    expect(post.userId).to.be.a("number");
    expect(post.id).to.be.a("number");
    expect(post.title).to.be.a("string").and.not.be.empty;
    expect(post.body).to.be.a("string").and.not.be.empty;
  });
});

test("every returned post matches the requested user", function () {
  const posts = res.getBody();

  expect(posts.every(function (post) {
    return post.userId === 1;
  })).to.eql(true);
});
```

Запустите запрос ещё раз. Все проверки должны пройти.

Почему используются две отдельные проверки:

- `every post has the expected contract` проверяет форму и типы каждого объекта;
- `every returned post matches the requested user` проверяет смысл фильтра.

Первая относится к контракту данных, вторая — к поведению endpoint. Одна не заменяет другую.

## 7. Увидьте опасность слабого зелёного теста — 8 минут

Откройте `08-get-posts-by-user` и временно отключите или закомментируйте два теста:

- `every post has the expected contract`;
- `every returned post matches the requested user`.

Оставьте только проверки статуса, `Content-Type` и первого `userId`. Отправьте запрос.

Набор остаётся зелёным, но теперь он не обнаружит ситуации, когда:

- один из последующих элементов имеет другой `userId`;
- у второго элемента отсутствует `title`;
- `id` одного из элементов неожиданно стал строкой;
- массив содержит элемент неверного типа.

Зелёный цвет означает только то, что выполнены записанные проверки. Он не доказывает, что тестировщик записал все важные ожидания.

Верните оба JavaScript-теста, сохраните запрос и повторите запуск. Не оставляйте намеренно ослабленную версию в коммите.

Запишите в `notes/session-04.md` один пример дефекта, который пропустила бы слабая версия.

Проверьте:

- текущая ветка — `main`;
- все девять запросов проходят;
- рабочее дерево чистое;
- в истории виден учебный коммит и merge-коммит `merge: complete lesson 4`.

Пример формы истории:

```text
*   ... (HEAD -> main) merge: complete lesson 4
|\
| * ... (lesson/04-contract-regression) test: add HTTP contract regression scenarios
|/
* ... предыдущий коммит main
```

Хэши и предыдущие сообщения у вас будут другими.

После успешной проверки локальную рабочую ветку можно удалить:

```bash
git branch -d lesson/04-contract-regression
```

Удаление необязательно. Оно не удаляет слитые коммиты из `main`.

> Если после merge обнаружена ошибка, не исправляйте её новым прямым коммитом в `main`. Создайте ветку, например `fix/lesson-04-contract-check`, внесите исправление, повторите тесты и слейте исправленную ветку тем же способом.

## Если осталось время

### Вариант 1. Сделайте ожидание фильтра независимым от жёсткого числа

Сейчас JavaScript-тест сравнивает `post.userId` с числом `1`. Измените `postUserId` на `2` и посмотрите, какой тест упадёт.

Верните `postUserId = 1` перед основным коммитом. Полноценное чтение environment-переменных из скриптов Bruno и области видимости переменных будут темой следующего блока.

Цель эксперимента — увидеть связь между тестовыми данными и ожидаемым результатом, а не преждевременно усложнить тест.

### Вариант 2. Нарисуйте историю до и после merge

До слияния выполните:

```bash
git log --oneline --graph --decorate --all -8
```

Повторите команду после слияния и зарисуйте обе формы истории в `notes/session-04.md`. Отметьте:

- общий коммит, от которого создана ветка;
- учебный коммит в рабочей ветке;
- merge-коммит в `main`.
