# Блок 4. Занятие 13 — проектирование финтех-пилота: границы, требования и риски

**Продолжительность:** 120 минут

**Формат:** 25% обсуждение и моделирование, 60% практическое проектирование, 15% ревью

**Исходная ситуация:** после занятия 12 ученик умеет связывать требование, риск, test case, тестовые данные, автоматизированный запрос и результат запуска. Учебные проверки пока относятся преимущественно к публичному API. Перед реализацией портфолио-проекта необходимо определить, что именно делает финтех-сервис, какие правила считаются контрактом и какие ошибки наиболее опасны.

**Результат занятия:** ученик проектирует минимальный API цифрового кошелька как тестируемый продукт. Зафиксированы scope и ограничения, роли и ресурсы, основной пользовательский сценарий, правила денег и переводов, проверяемые требования с устойчивыми ID и приоритетная карта рисков. Для критичных правил намечены позитивные и негативные проверки. Команда получает основу для OpenAPI-контракта и подробных тест-кейсов следующих занятий.

## Главное правило занятия

Тесты нельзя проектировать по названиям endpoint без бизнес-контекста. Сначала нужно определить состояние системы и правила перехода между состояниями:

```text
роль пользователя
      |
      v
клиент -> KYC -> счёт -> исходный баланс
                         |
                         v
                 попытка перевода
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       выполнен       отклонён       повторён
          |              |              |
          v              v              v
  новые балансы    деньги целы    нет дубля
```

Каждое важное правило должно отвечать на вопросы:

1. При каких предусловиях оно действует?
2. Какое действие выполняет пользователь или система?
3. Какой наблюдаемый результат считается правильным?
4. Что обязано остаться неизменным при отказе?
5. Какой ущерб возможен при нарушении правила?
6. Каким позитивным и негативным тестом это будет доказано?

На этом занятии нельзя:

- начинать с создания `.bru`-запросов до согласования правил продукта;
- использовать `float` как модель денег или игнорировать валюту суммы;
- описывать требования словами «работает корректно» или «валидное значение»;
- объединять аутентификацию и авторизацию в одно правило;
- считать только HTTP-статус достаточным oracle для перевода;
- забывать об инварианте балансов при отклонённой операции;
- трактовать повтор с тем же ключом идемпотентности как новый перевод;
- включать реальные банковские реквизиты, персональные данные или секреты;
- превращать список endpoint в список тест-кейсов один к одному;
- пытаться покрыть все функции банка в первом MVP.

Работа выполняется в ветке `lesson/13-fintech-requirements`. Основные артефакты занятия — `docs/product-scope.md`, `docs/requirements.md` и `docs/risk-matrix.md`.

## Границы учебного MVP

В scope входят:

- вход пользователя;
- создание клиента;
- изменение KYC-статуса уполномоченной ролью;
- создание счёта;
- чтение счёта и баланса владельцем;
- перевод между двумя существующими счетами в одной валюте;
- проверка остатка, статуса счёта и дневного лимита;
- идемпотентная обработка команды перевода;
- единый контракт ошибок и correlation ID.

Вне scope:

- реальные карты и банковские реквизиты;
- обмен валют и курсы;
- комиссии, проценты и кредитный лимит;
- возвраты, chargeback и dispute flow;
- реальные regulatory checks;
- внешние платёжные провайдеры;
- нагрузочное тестирование и распределённые транзакции;
- реальные персональные данные.

## Цель

Дать авторизованному клиенту возможность безопасно перевести деньги между двумя счетами в одной валюте и однозначно проверить результат операции.

## 3. Определите роли, ресурсы и доверительные границы — 12 минут

### Роли

| Роль | Разрешённые действия | Запрещённые действия |
|---|---|---|
| `customer` | читать собственные счета, создавать перевод со своего счёта | менять KYC, читать чужой счёт |
| `compliance` | менять KYC-статус клиента | создавать перевод от имени клиента |
| `service` | выполнять внутреннюю обработку команды | действовать без проверяемой service identity |

### Ресурсы

- `Customer`: владелец счетов и субъект KYC;
- `Account`: счёт с владельцем, валютой, статусом и балансом;
- `Transfer`: команда и результат перемещения денег;
- `Error`: безопасное описание отказа с машинным кодом и correlation ID.

Для каждого действия ответьте: кто предъявляет identity, какая роль требуется, как подтверждается владение объектом и какие поля ответа нельзя раскрывать. Валидный Bearer token не разрешает читать любой `accountId`.

## 4. Постройте модель состояний — 12 минут

Клиент и KYC:

```text
PENDING -> VERIFIED
   |
   +----> REJECTED
```

Счёт:

```text
ACTIVE -> BLOCKED -> ACTIVE
```

Перевод:

```text
PENDING -> COMPLETED
   |
   +----> REJECTED
```

Определите, кто может выполнять переходы. Для каждого запрещённого перехода запишите реакцию и инвариант. Например, перевод с `BLOCKED`-счёта отклоняется, а оба баланса остаются прежними.

## 5. Зафиксируйте модель денег и инварианты — 15 минут

Для пилота примите решение:

- сумма передаётся целым количеством minor units;
- `1000` означает `10.00` для валюты с двумя десятичными знаками;
- валюта хранится отдельно как трёхбуквенный код;
- арифметика не выполняется через binary floating point;
- `amount` должен быть положительным целым числом.

Пример безопасного payload:

```json
{
  "sourceAccountId": "acc-source-001",
  "targetAccountId": "acc-target-001",
  "amount": 1000,
  "currency": "EUR"
}
```

Инварианты успешного перевода без комиссии:

```text
sourceAfter = sourceBefore - amount
targetAfter = targetBefore + amount
sourceBefore + targetBefore = sourceAfter + targetAfter
```

Инварианты отказа:

```text
sourceAfter = sourceBefore
targetAfter = targetBefore
новый COMPLETED transfer не создан
```

Наметьте классы для будущих тестов:

| Класс | Пример | Ожидание |
|---|---:|---|
| минимальная валидная сумма | `1` | разрешено при выполнении остальных условий |
| ноль | `0` | validation error |
| отрицательная сумма | `-1` | validation error |
| дробное значение | `10.5` | validation error |
| строка вместо числа | `"1000"` | validation error, если coercion не разрешён |
| сумма равна остатку | весь доступный баланс | разрешено, если лимит не нарушен |
| сумма выше остатка | остаток + 1 | insufficient funds |

## 6. Определите правила разрешения перевода — 13 минут

Зафиксируйте независимые бизнес-проверки:

1. Пользователь аутентифицирован.
2. Пользователь вправе создавать перевод с исходного счёта.
3. Оба счёта существуют и активны.
4. Валюта команды совпадает с валютой обоих счетов.
5. Сумма соответствует контракту.
6. Доступного остатка достаточно.
7. Операция не превышает дневной лимит.
8. Идемпотентность команды не нарушена.

Для учебного пилота примите дневной лимит `100_000` minor units:

| Уже переведено сегодня | Новая сумма | Итог | Ожидание |
|---:|---:|---:|---|
| `40_000` | `59_999` | `99_999` | разрешено |
| `40_000` | `60_000` | `100_000` | разрешено |
| `40_000` | `60_001` | `100_001` | отклонено |

Не смешивайте дневной лимит с текущим балансом: в boundary-тестах баланс должен быть достаточным, иначе нельзя определить, какое правило вызвало отказ.

## 7. Опишите семантику идемпотентности — 12 минут

| Сценарий | Ожидаемый результат |
|---|---|
| Первый запрос с новым ключом | создан один перевод |
| Повтор того же ключа и идентичного payload | возвращён исходный результат, новый перевод не создан |
| Повтор того же ключа с другим payload | конфликт, деньги не изменены |
| Новый ключ с тем же payload | новая команда; применяется обычная бизнес-валидация |
| Отсутствующий ключ | validation error, если заголовок обязателен |

Для пилота идентичность payload образуют `sourceAccountId`, `targetAccountId`, `amount` и `currency` после согласованной нормализации.

Oracle идемпотентности проверяет не только HTTP-ответ:

- идентификатор операции совпадает с исходным при безопасном повторе;
- число созданных переводов не увеличилось;
- баланс не списан второй раз;
- изменённый payload не применён частично.

## 8. Разделите доступ и контракт ошибок — 12 минут

### Authentication и authorization

| Ситуация | Статус | Смысл |
|---|---:|---|
| token отсутствует или невалиден | `401` | identity не подтверждена |
| identity подтверждена, но роль не разрешает действие | `403` | недостаточно прав |
| клиент читает чужой счёт | `403` или маскирующий `404` | команда выбирает один вариант и применяет его последовательно |

Для object-level access недостаточно роли `customer`: API сверяет identity с владельцем конкретного счёта.

### Единый error contract

```json
{
  "code": "INSUFFICIENT_FUNDS",
  "message": "Transfer cannot be completed",
  "correlationId": "corr-synthetic-001"
}
```

Требования к ошибке:

- `code` стабилен и пригоден для автоматической проверки;
- `message` не раскрывает токены, stack trace, SQL, внутренние пути и чужие данные;
- `correlationId` присутствует и позволяет найти запрос в журнале;
- один тип ошибки имеет одинаковую структуру;
- ожидаемый бизнес-отказ не возвращается как `500`.

## 9. Запишите требования и acceptance criteria — 12 минут

Добавьте в `docs/requirements.md` раздел `Fintech pilot`:

| Requirement ID | Краткое правило |
|---|---|
| `REQ-AUTH-001` | API отклоняет запрос без валидной identity |
| `REQ-KYC-001` | только разрешённая роль меняет KYC-статус |
| `REQ-ACC-001` | клиент читает только разрешённый ему счёт |
| `REQ-ACC-002` | заблокированный счёт не участвует в переводе |
| `REQ-TRF-001` | валидный перевод атомарно изменяет два баланса |
| `REQ-TRF-002` | при недостаточном остатке деньги не изменяются |
| `REQ-TRF-003` | перевод разрешён только для согласованной валюты |
| `REQ-TRF-004` | дневной лимит проверяется включительно на границе |
| `REQ-IDEM-001` | одинаковый повтор не создаёт вторую операцию |
| `REQ-IDEM-002` | тот же ключ с другим payload вызывает конфликт |
| `REQ-ERR-001` | ошибки соответствуют единому безопасному контракту |

Шаблон подробного требования:

```markdown
### REQ-TRF-002 — недостаточный остаток

Если сумма перевода превышает доступный остаток исходного счёта, API должно отклонить перевод с машинным кодом `INSUFFICIENT_FUNDS`.

#### Acceptance criteria

- сумма, равная доступному остатку, обрабатывается по обычным правилам;
- сумма на одну minor unit больше остатка отклоняется;
- баланс исходного счёта не меняется;
- баланс целевого счёта не меняется;
- операция со статусом `COMPLETED` не создаётся;
- ответ соответствует error contract и содержит correlation ID.
```

Проверьте каждую формулировку: есть предусловие, наблюдаемый результат, инвариант отказа, нет неоднозначных слов и деталей реализации теста.

## 10. Постройте карту рисков — 8 минут

Добавьте или расширьте `docs/risk-matrix.md`:

| Risk ID | Риск | Вероятность | Влияние | Priority | Requirements | Минимальная проверка |
|---|---|---:|---:|---:|---|---|
| `R-MONEY-01` | двойное списание при повторе | medium | critical | P0 | `REQ-IDEM-001` | повторить команду и сравнить transfer ID и балансы |
| `R-MONEY-02` | изменён только один баланс | low | critical | P0 | `REQ-TRF-001` | проверить оба баланса и сохранение общей суммы |
| `R-MONEY-03` | деньги изменились после отказа | medium | critical | P0 | `REQ-TRF-002`, `REQ-TRF-004` | сравнить before/after обоих счетов |
| `R-LIMIT-01` | ошибка на точной границе лимита | medium | high | P1 | `REQ-TRF-004` | ниже, ровно и выше лимита |
| `R-AUTHZ-01` | клиент читает чужой счёт | medium | critical | P0 | `REQ-ACC-001` | владелец и другой клиент запрашивают один ID |
| `R-STATE-01` | перевод с заблокированного счёта | medium | high | P1 | `REQ-ACC-002` | blocked source и blocked target |
| `R-CURR-01` | перевод между несовместимыми валютами | medium | high | P1 | `REQ-TRF-003` | currency mismatch без изменения балансов |
| `R-ERROR-01` | ошибка раскрывает внутренние данные | low | high | P1 | `REQ-ERR-001` | схема и запрещённые поля |

Приоритеты упражнения:

- `P0`: возможна потеря/создание денег или доступ к чужим данным;
- `P1`: критичное бизнес-правило нарушено без прямой потери денег;
- `P2`: ухудшается диагностичность или некритичная совместимость;
- `P3`: косметическая или маловероятная проблема вне основного пути.

Для каждого `P0`-риска наметьте минимум один позитивный и один негативный тест. Подробные test case ID будут оформлены на следующем занятии.

## Типичные проблемы и диагностика

| Симптом | Проблема | Как исправить |
|---|---|---|
| «Перевод работает корректно» | требование нельзя проверить | добавить предусловия, результат и инварианты |
| Требования повторяют endpoint | потеряны бизнес-правила | описать состояние и риск, а не только HTTP-операцию |
| Проверяется только баланс source | возможна частичная операция | проверить source, target и сохранение общей суммы |
| При отказе проверяется только `4xx` | деньги могли измениться | добавить before/after и отсутствие completed transfer |
| `100000` считается невалидным | не определена граница | явно записать `<= limit` |
| Повтор создаёт новый transfer ID | идемпотентность не определена | вернуть исходный результат без второго списания |
| Любой customer читает любой счёт | роль подменила ownership check | проверять identity и владельца объекта |
| `403` и `404` чередуются случайно | нет политики маскирования | выбрать единый контракт |
| В требованиях реальные ФИО или карты | небезопасные данные | заменить синтетическими ID |
| Все риски объявлены P0 | приоритет не помогает | применить критерии ущерба и отделить P1/P2 |
| OpenAPI пишется до решения о minor units | закрепляется случайная модель | сначала согласовать предметные правила |

## Контрольные вопросы

1. Почему endpoint сам по себе не является бизнес-требованием?
2. Чем аутентификация отличается от авторизации и проверки владения объектом?
3. Почему денежная сумма моделируется через minor units?
4. Какой инвариант доказывает сохранение общей суммы?
5. Что обязано остаться неизменным при недостаточном остатке?
6. Почему «ровно лимит» и «выше на одну minor unit» — разные тесты?
7. Чем безопасный повтор отличается от нового запроса с новым ключом?
8. Почему изменённый payload с прежним ключом вызывает конфликт?
9. Почему проверки `status === 400` недостаточно для error contract?
10. Как риск P0 влияет на будущий smoke- или regression-набор?
11. Какие решения занятия должны попасть в OpenAPI-контракт?
12. Какие части продукта оставлены за пределами MVP и почему?
