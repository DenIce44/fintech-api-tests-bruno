# План обучения API-тестированию с Bruno

## Цель

За 8 недель при нагрузке 6–8 часов в неделю собрать и опубликовать на GitHub портфолио-проект `fintech-api-tests-bruno`: воспроизводимый набор API-тестов для учебного платёжного сервиса.

Итоговый репозиторий должен показывать, что автор умеет:

- анализировать API и превращать требования в тесты;
- работать с REST, JSON, HTTP-кодами, заголовками и авторизацией;
- писать проверки и JavaScript-тесты в Bruno;
- строить связанные сценарии с переменными и pre/post-response scripts;
- тестировать характерные для финтеха правила: денежную точность, лимиты, идемпотентность, остатки и права доступа;
- запускать smoke и regression-наборы из Bruno CLI;
- хранить тесты в Git и запускать их в GitHub Actions;
- публиковать понятные отчёты и документацию.

## Формат обучения

- Темп: 4 занятия по 90 минут в неделю.
- Соотношение: около 25% теории и 75% практики.
- Каждый этап заканчивается артефактом в Git: коллекцией, тест-кейсами, отчётом или документацией.
- ИИ помогает с идеями, ревью и черновиками. Все сгенерированные тесты нужно понять, запустить и при необходимости исправить вручную.
- Для практики не используются реальные банковские данные, карты, ключи или персональные данные.

## Инструменты

Обязательный набор:

- Bruno Desktop;
- Bruno CLI;
- Node.js LTS и npm;
- Git и GitHub;
- редактор кода;
- Codex как ИИ-помощник;
- учебный локальный fintech API или управляемый mock-сервис;
- GitHub Actions.

Опционально:

- Docker Desktop — чтобы одинаково запускать демо-API на разных компьютерах;
- GitHub Copilot — если он уже используется. Подключать несколько ИИ-помощников одновременно для обучения не требуется.

## Этап 0. Установка и проверка окружения

**Срок:** 1–2 дня.

### Изучить

- чем Bruno Desktop отличается от Bruno CLI;
- что такое коллекция, запрос и environment;
- базовые команды Git: `status`, `add`, `commit`, `push`;
- почему секреты нельзя хранить в репозитории.

### Выполнить

1. Создать аккаунт GitHub и настроить Git, если этого ещё нет.
2. Установить Node.js LTS. Документация Bruno CLI требует Node.js 18 или новее.
3. Установить Bruno Desktop.
4. Создать локальную папку `fintech-api-tests-bruno` и открыть её в Codex.
5. Инициализировать npm-проект и установить Bruno CLI локально, чтобы версия фиксировалась в репозитории:

   ```bash
   npm init -y
   npm install --save-dev @usebruno/cli
   npx bru --version
   ```

6. Создать в Bruno коллекцию `fintech-api` внутри папки `bruno/fintech-api`.
7. Создать environment `local` с переменной `baseUrl`.
8. Добавить `.gitignore`; секретные environment-файлы и отчёты исключить из Git.
9. Добавить `AGENTS.md` с правилами для ИИ:

   - не добавлять секреты и реальные персональные данные;
   - сохранять тесты в `.bru`;
   - использовать Safe Mode, если нет обоснованной причины включать Developer Mode;
   - после генерации запускать изменённые тесты;
   - объяснять, какое требование покрывает каждая проверка.

### Критерий готовности

- команды `git --version`, `node --version`, `npm --version` и `npx bru --version` выполняются;
- Bruno открывает коллекцию из папки проекта;
- в Git нет токенов, паролей и локальных секретов;
- создан первый коммит `chore: initialize Bruno test project`.

## Этап 1. HTTP и первые тесты

**Срок:** неделя 1.

### Изучить

- методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`;
- URL, query/path parameters, headers и JSON body;
- группы кодов `2xx`, `4xx`, `5xx`;
- разницу между функциональной проверкой и проверкой контракта;
- структуру Arrange–Act–Assert.

### Практика

1. На безопасном echo API создать запросы `GET` и `POST`.
2. Использовать `{{baseUrl}}` вместо жёстко заданного адреса.
3. Добавить декларативные assertions:

   - ожидаемый status code;
   - `Content-Type` содержит `application/json`;
   - обязательное поле есть в body;
   - значение имеет ожидаемый тип.

4. Повторить проверки JavaScript-тестами с Chai.
5. Создать намеренно падающий тест, прочитать ошибку и исправить его.
6. Запустить коллекцию сначала из интерфейса Bruno, затем из терминала:

   ```bash
   npx bru run bruno/fintech-api -r --env local
   ```

### Артефакт

- папка `00-learning-basics` с 5–7 простыми запросами;
- короткий `notes/http-basics.md` с примерами запросов и ожидаемых ответов.

### Критерий готовности

Ученик может без подсказки объяснить каждый запрос и написать четыре базовые проверки ответа.

## Этап 2. Основные возможности Bruno

**Срок:** неделя 2.

### Изучить

- collection, folder, request и порядок выполнения;
- environment, collection, runtime и request variables;
- assertions и JavaScript tests;
- pre-request и post-response scripts;
- наследование настроек и авторизации;
- импорт OpenAPI 3.

### Практика

1. Завести environments `local` и `mock`; публичным оставить только шаблон без секретов.
2. Сохранить значение из одного ответа в runtime variable и использовать его в следующем запросе.
3. Добавить теги `smoke`, `regression`, `negative`.
4. Импортировать небольшой OpenAPI 3 файл и сравнить созданные запросы с контрактом.
5. Добавить тесты на время ответа и структуру ошибки.
6. Запустить отдельные наборы:

   ```bash
   npx bru run bruno/fintech-api -r --env local --tags=smoke
   npx bru run bruno/fintech-api -r --env local --tags=regression
   ```

### Артефакт

- коллекция с несколькими папками и связанным сценарием;
- `docs/test-strategy.md` с описанием уровней smoke/regression/negative.

### Критерий готовности

Один запуск создаёт данные, извлекает идентификатор, использует его в следующем запросе и корректно проверяет результат.

## Этап 3. Авторизация, данные и негативные сценарии

**Срок:** неделя 3.

### Изучить

- Bearer token, Basic Auth и основы OAuth 2.0;
- отличие `401 Unauthorized` от `403 Forbidden`;
- позитивное, негативное и граничное тестирование;
- классы эквивалентности и анализ граничных значений;
- безопасное хранение токенов в локальном окружении и GitHub Secrets.

### Практика

1. Создать запрос логина и сохранять токен во временную переменную.
2. Добавить запросы с отсутствующим, просроченным и некорректным токеном.
3. Подготовить таблицу тестовых данных для валидных и невалидных сумм, валют и идентификаторов.
4. Проверить обязательные поля, пустые строки, слишком длинные значения и неверные типы.
5. Запустить небольшой data-driven набор через JSON или CSV из Bruno CLI.

### Артефакт

- `test-data/` без чувствительных данных;
- `docs/test-cases.md` с идентификаторами вида `AUTH-001`, `TRF-001`;
- коллекция с позитивными и негативными тестами авторизации.

### Критерий готовности

Тесты стабильно различают проблемы аутентификации, авторизации и валидации входных данных.

## Этап 4. Проектирование финтех-пилота

**Срок:** неделя 4.

### Учебный продукт

Минимальный API цифрового кошелька:

- `POST /auth/login`;
- `POST /customers`;
- `PATCH /customers/{id}/kyc`;
- `POST /accounts`;
- `GET /accounts/{id}`;
- `GET /accounts/{id}/balance`;
- `POST /transfers`;
- `GET /transfers/{id}`.

### Бизнес-правила

- деньги передаются целым количеством минимальных единиц или строкой с фиксированной точностью, без вычислений через неточный floating point;
- перевод запрещён при недостаточном остатке, заблокированном счёте или неразрешённой валюте;
- дневной лимит проверяется на границе: ниже лимита, ровно лимит, выше лимита;
- повтор одного запроса с тем же `Idempotency-Key` не создаёт второй перевод;
- повтор ключа с другим payload возвращает конфликт;
- клиент без нужной роли не читает чужой счёт;
- после успешного перевода списание и зачисление согласованы, общая сумма денег сохраняется;
- ошибка имеет единый контракт: код, сообщение, correlation/request ID.

### Спроектировать

1. Карту рисков: сумма, валюта, лимиты, идемпотентность, конкурентность, права доступа, аудит.
2. Матрицу `требование → риск → тест → тег`.
3. Не менее 30 тест-кейсов:

   - 8 happy path;
   - 12 negative;
   - 6 boundary;
   - 4 security/authorization.

4. OpenAPI 3 контракт демо-API.
5. Наборы `smoke` и `regression`.

### Артефакт

- `openapi/fintech-api.yaml`;
- `docs/requirements.md`;
- `docs/risk-matrix.md`;
- `docs/test-cases.md`.

### Критерий готовности

Для каждого критичного бизнес-правила существует хотя бы один позитивный и один негативный тест.

## Этап 5. Реализация Bruno-коллекции пилота

**Срок:** неделя 5.

### Структура коллекции

```text
bruno/fintech-api/
├── 00-health/
├── 01-auth/
├── 02-customers/
├── 03-accounts/
├── 04-transfers/
├── 05-negative/
├── 06-security/
├── environments/
├── bruno.json
└── collection.bru
```

### Реализовать

- health-check и логин;
- создание клиента, KYC и счёта;
- получение баланса до операции;
- успешный перевод и проверку его статуса;
- проверку балансов после перевода;
- duplicate request с `Idempotency-Key`;
- недостаточный остаток, неверную валюту и превышение лимита;
- доступ к чужому счёту;
- проверки статуса, схемы, заголовков, времени ответа и бизнес-инвариантов;
- очистку или уникализацию тестовых данных.

### Критерий готовности

- smoke-набор проходит за один последовательный запуск;
- повторный запуск не падает из-за уже созданных данных;
- regression-набор содержит минимум 30 осмысленных проверок;
- каждый тест связан с идентификатором требования или тест-кейса.

## Этап 6. Надёжность и безопасность тестов

**Срок:** неделя 6.

### Изучить и проверить

- отсутствие секретов в Git и отчётах;
- маскирование `Authorization`, cookies и токенов;
- предсказуемость тестовых данных;
- независимость тестов там, где это возможно;
- повторяемость и причины flaky tests;
- базовые проверки OWASP API Security: object-level authorization, excessive data exposure, rate limiting и безопасные ошибки;
- race condition как дополнительный сценарий, а не обязательная часть smoke.

### Практика

1. Выполнить повторный прогон коллекции 5 раз.
2. Исправить тесты, зависящие от случайного порядка или старых данных.
3. Проверить, что логи и отчёты не раскрывают токены.
4. Добавить `docs/bugs/` минимум с тремя учебными баг-репортами:

   - заголовок и severity;
   - предусловия;
   - шаги;
   - фактический и ожидаемый результат;
   - request/response без секретов;
   - ссылка на связанный тест.

### Критерий готовности

Пять последовательных локальных запусков дают одинаковый результат, а сканирование репозитория не находит секретов.

## Этап 7. CLI, отчёты и GitHub Actions

**Срок:** неделя 7.

### Реализовать локальные команды

Добавить scripts в `package.json`:

```json
{
  "scripts": {
    "test:api:smoke": "bru run bruno/fintech-api -r --env local --tags=smoke --bail",
    "test:api:regression": "bru run bruno/fintech-api -r --env local --tags=regression --reporter-junit reports/results.xml --reporter-html reports/results.html"
  }
}
```

### Настроить CI

Workflow `.github/workflows/api-tests.yml` должен:

1. запускаться на `push`, `pull_request` и вручную;
2. получать код;
3. поднимать демо-API;
4. дождаться health endpoint;
5. запускать Bruno CLI в Safe Mode;
6. формировать JUnit и HTML-отчёты;
7. загружать отчёты как artifacts даже при падении тестов;
8. завершаться с ошибкой при падении обязательных тестов.

Можно использовать официальный `usebruno/bruno-cli-action@v1` или обычную установку Node.js и запуск npm scripts. Версию Bruno CLI следует зафиксировать, а не оставлять неограниченный `latest`.

### Критерий готовности

- новый pull request автоматически запускает smoke-тесты;
- падение assertion делает workflow красным;
- из workflow можно скачать JUnit и HTML-отчёт;
- в CI используются только GitHub Secrets и публичные тестовые данные.

## Как использовать Codex во время обучения

Подходящие задачи для ИИ:

- превратить бизнес-правило в список позитивных, негативных и граничных сценариев;
- проверить `.bru`-файл на слабые assertions;
- предложить тесты на идемпотентность, лимиты и авторизацию;
- объяснить упавший тест по request/response;
- сопоставить OpenAPI и Bruno-коллекцию;
- подготовить черновик workflow и README;
- провести финальное ревью репозитория как интервьюер QA Automation.

Контрольный промпт:

> Проанализируй этот Bruno-запрос и связанное бизнес-требование. Сначала перечисли недостающие риски, затем предложи минимальный набор проверок. Не добавляй секреты. Используй Bruno/Chai API. Для каждой проверки укажи, какое требование она покрывает. После изменения запусти затронутый набор и сообщи фактический результат.

Правило качества: код, который ученик не может объяснить, ещё не считается частью портфолио.

## Первый учебный спринт: ближайшие 90 минут

Подробная пошаговая инструкция: [Блок 1. Занятие 1 — первый API-запрос и первые проверки в Bruno](lessons/block-01/lesson-01.md).

1. Установить Bruno Desktop, Node.js LTS и Git.
2. Проверить версии инструментов.
3. Создать локальный репозиторий и npm-проект.
4. Установить `@usebruno/cli` как dev dependency.
5. Создать коллекцию и environment `local`.
6. Добавить один `GET`-запрос к echo API через `{{baseUrl}}`.
7. Проверить status `200`, JSON content type и обязательное поле ответа.
8. Запустить запрос в UI и всю коллекцию через CLI.
9. Сделать первый осмысленный commit.
10. В `notes/session-01.md` записать три вещи: что получилось, что было непонятно, какую ошибку удалось исправить.
